> https://doi.org/10.5281/zenodo.24217263).

The statement cites the **concept DOI** `10.5281/zenodo.24217263`, which always
resolves to the newest archived release. The version DOI of the release that
matches the manuscript at submission time is `10.5281/zenodo.24217264`
(`v1.0.0`); later releases keep the same concept DOI.

Why the concept DOI: a version DOI is an immutable snapshot, and the snapshot
cannot contain the DOI it is being assigned (the DOI is minted at publish time).
Citing the concept DOI keeps the link inside the article consistent with the
archive it opens, and it stays correct when a new release is published.

## What the journal actually asks for (Option C)

Neurocomputing applies Elsevier's research-data policy **Option C**, which asks
authors to

1. deposit the research data in a relevant repository,
2. cite and link the dataset in the article, and
3. if that is not possible, state the reason why the data cannot be shared.

Two points matter here:

* **"Research data" includes code.** Elsevier defines research data as
  "observations or experimentation that validate research findings, which may
  also include software, code, models, algorithms, protocols, methods". So the
  reproducible code counts as the data deposit here.
* **The link must work for reviewers, not only after acceptance.** If the
  repository is private during review, a reviewer cannot verify the claim.
  Therefore the repository has to be reachable at submission time, or the
  statement must say that access is available on request.

## What a DOI is, and why people mention it

A DOI (Digital Object Identifier) is a permanent identifier — like
`10.5281/zenodo.1234567` — that resolves to the archived copy of a specific
version of your repository. The difference from a GitHub URL:

| | GitHub URL | DOI |
|---|---|---|
| Stable over time | can change if the repo is renamed or deleted | permanent, cannot be reused |
| Versioned archive | no; the branch keeps moving | yes; one DOI per release |
| Citable in a reference list | awkward | standard practice |
| Cost / effort | zero | free via Zenodo, ~5 minutes |

Elsevier's Guide for Authors says DOIs are *encouraged* ("where available include
Digital Object Identifiers, as they provide a permanent link … and improve the
discoverability"). They are not mandatory. So:

* **Minimum to satisfy the policy:** a working public repository URL. The text
  links the repository; the statement becomes true once the repository is public.
* **Recommended:** archive a tagged release on Zenodo to obtain a DOI, then cite
  that DOI. This protects the paper if the repository later changes.

## Recommended procedure (about 10 minutes, free)

1. Push the repository to GitHub, make it **public**, and confirm that `LICENSE`
   and `CITATION.cff` are present (Zenodo reads `CITATION.cff` for the record
   metadata).
2. Log in to <https://zenodo.org> **with the GitHub account** (profile menu →
   *Linked accounts*, or sign in with GitHub).
3. Open the profile menu → **GitHub** → **Sync now**, then toggle the slider of
   the new repository to enable it.
4. On GitHub, create a release whose tag matches `version:` in `CITATION.cff`
   (for example `v1.0.0`). Zenodo ingests the release tarball automatically and
   mints a DOI.
5. Zenodo creates **two** identifiers:
   * a **version DOI** (`10.5281/zenodo.NNNNNNN`) that always points to that
     exact release — cite this in the paper for reproducibility;
   * a **concept DOI** that always resolves to the newest release.
6. Put the version DOI in `sections/declarations.tex`, next to the repository
   URL:
   `\url{https://github.com/<user>/<repo>} (archived at
   \url{https://doi.org/10.5281/zenodo.NNNNNNN})`.
7. Rebuild (`./build.sh`, `./make_submission.sh`) so the PDF, the proof and the
   zip all carry the DOI.

Notes:

* Zenodo only archives releases created **after** the repository is enabled; it
  does not retroactively archive existing tags.
* If the release fails, Zenodo reports the error in the repository view; the
  usual cause is an invalid `CITATION.cff`.
* A manual upload (a single `.zip` of the release) is also accepted and produces
  a DOI immediately, but the GitHub integration keeps the provenance link.

## Optional: citing the datasets as data references

Elsevier allows `[dataset]`-prefixed entries in the reference list. This is not
required, since the three public datasets are already cited as ordinary
references (Angwin et al. for COMPAS, Hofmann for German Credit, Kohavi for UCI
Adult). If you prefer explicit data references, add the repository name,
version, year, and persistent identifier to each entry.
